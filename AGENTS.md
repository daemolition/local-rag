# AGENTS.md

High-signal guidance for OpenCode sessions in this repo.

## Project in one line

German Flask RAG app with SSE chat, user accounts with fixed roles (admin/editor/user), SQLAlchemy settings/chat/document tracking, Qdrant hybrid search (dense + sparse/BM25), Pandas analytics tools, and Ollama/OpenAI-compatible LLMs.

## Entry points and run commands

```bash
# Install dependencies (uses uv)
uv sync

# Windows (no admin required; auto-downloads qdrant.exe)
start.bat
# Or directly
python run_windows.py              # with local Qdrant
python run_windows.py --no-qdrant  # if you run Qdrant separately

# Linux / Docker
alembic upgrade head
python run_linux.py
docker-compose up --build
```

- Windows default URL: `http://127.0.0.1:5000` (localhost only; no firewall prompt).
- Linux/Docker host port: `docker-compose up` maps `8083:5000` (host:container) — the app is on `http://localhost:8083`, not 5000. The README's "http://localhost:5000" Docker note is stale.
- Linux manual (`python run_linux.py`, no Docker) binds `0.0.0.0:5000`.
- Default login: user `admin`, password `admin` (seeded once by `app/users.py:ensure_admin_user` when the `users` table is empty; the password is the existing `APP_PASSWORD_HASH`, default `admin` / `ADMIN_PASSWORD` on a fresh DB, so installs keep their set password). Session cookie holds only `user_id` (`app/auth.py:current_user` loads role/active state per request; deactivating a user ends their session). Roles are ordered `user` < `editor` < `admin`: `@require_role("editor")` guards knowledge/document/vector-DB/stats endpoints, `@require_role("admin")` guards settings, connections/models and the legacy `/user/*` blueprint (a `before_request` gate); chat, own sessions, attachments, `GET /api/knowledge`, summaries and `GET /api/models` need only login. Chats are private per user (`sessions.user_id`; foreign IDs return 404, including `/chat/stop` and attachments). Login is throttled per username (5 failures / 5 min, in-memory). Non-admins get `/api/models` without prompt/params (`knowledge_locked` flag only). Not built yet: OIDC.
- Both `run_windows.py` and `run_linux.py` run `alembic upgrade head` automatically before starting the server.

## Database: Postgres (SQLite only for dev/tests) and Alembic baseline

- The initial migration (`alembic/versions/0001_initial_schema_and_admin_seed.py`) creates all tables and seeds an admin user (`admin` / `admin`).
- Migration `0002_single_user_conversion.py` drops the original `users` table (re-introduced in `0010`), moves the admin password hash into the `APP_PASSWORD_HASH` setting row, and removes all `user_id` FKs (single-user). `0003_embedding_model_prefix.py` rewrites `EMBEDDING_MODEL` to the HF-org-prefixed form fastembed needs.
- `app.db` may already exist, created by `DatabaseService` calling `Base.metadata.create_all()` in `app/__init__.py` (not by Alembic). On an existing `app.db`, `alembic upgrade head` fails with "table already exists" — run `alembic stamp head` to mark it as migrated without executing DDL, or delete `app.db` to start fresh.
- `run_windows.py` / `run_linux.py` run `alembic upgrade head` automatically before starting the server; on a fresh DB this creates the schema + admin seed.

## Releases and versioning

- Version source of truth: `pyproject.toml`. `scripts/release.py` (stdlib only, tested in `tests/test_release.py`) keeps `frontend/package.json`, `frontend/package-lock.json` and the project block in `uv.lock` in sync: `current`, `check [--tag vX.Y.Z]`, `bump patch|minor|major|X.Y.Z [--dry-run]`, `notes [--version X.Y.Z]`, `publish [--yes]`. `bump` requires a clean tree (untracked files count) on `master` (`--branch` overrides), moves `## [Unreleased]` in `CHANGELOG.md` to the new version (or generates it from Conventional Commits since the last `v*` tag), commits `chore(release): vX.Y.Z` and creates an annotated tag. With no `v*` tag yet, `bump 0.1.0` (same version) is the first release. `publish` only prints commands without `--yes`.
- `.github/workflows/ci.yml` (tests + frontend build on push to master / PRs) and `release.yml` (on tag `vX.Y.Z`: `release.py check --tag`, tests, build, then `gh release create` with the changelog section). The script never creates the GitHub release itself. All actions are pinned to full commit SHAs (a test enforces it; Dependabot keeps them current), checkouts use `persist-credentials: false`, and only the last `release` job has `contents: write` while `verify` (tests, build) runs read-only. Keep a non-empty changelog section per released version: the release workflow fails without one.
- `app/version.py` reads the version from `pyproject.toml` (fallback env `APP_VERSION`); exposed as `GET /api/version`, in `/health`, and in the sidebar/account dialog.
- Never tag, commit or push on your own initiative; the user decides when v0.x is released.

## Frontend (React SPA)

- The UI is a React 19 + TypeScript SPA under `frontend/` (Vite + Tailwind v4 via `@tailwindcss/vite`, shadcn/ui components). It builds directly to `app/static/` (Vite `base: /static/`); Flask serves that directory and the 404 fallback handler in `app/routes.py:spa_fallback()` returns `index.html` for client-side routes (true catch-all; `/api/`, `/static/`, `/user/`, `/ws/` and non-GET are excluded). There are **no Jinja templates for the app shell anymore** — `frontend/index.html` is the only HTML entry point.
- Build: `cd frontend && npm install && npm run build` (runs `scripts/clean-static.mjs` first, then `tsc -b && vite build` → `app/static/`). Dev: `npm run dev` on :5173 with proxy to Flask on :5000; run the backend separately. The Vite proxy must only cover backend paths (`/api`, `/chat`, `/user`, `/logout`, `/health`, `/ws`) — client routes stay on the dev server.
- JSON API lives in `app/api_routes.py` (`/api/*`) and uses `auth_required_api`/`require_role` (`app/auth.py`) which return `401` JSON instead of redirecting to `/login`. The legacy `/user/*` HTML routes and `/chat`, `/chat/stop`, `/api/stt`, `/api/ingestion-status`, `/ws/stt-stream`, `/health` still exist and are reused by the SPA.
- Design tokens (ChatGPT-like neutrals, dark mode via `<html class="dark">`) are defined in `frontend/src/index.css` under `@theme` (`--color-surface`, `--color-primary`, `--color-border-base` …) + shadcn semantic tokens bridged onto them. **Do not** add per-element `dark:` variants — extend the tokens instead. Theme bootstrap runs inline in `frontend/index.html` before first paint (FOUC avoidance); `src/lib/theme.ts` + `src/context/ThemeContext.tsx` handle runtime switching. The server injects `UI_THEME` into the index via `serve_spa()` (placeholder `__RAG_UI_THEME__`).
- The Docker build is multi-stage: a `node:22-slim` stage runs `npm ci && npm run build` and the resulting `app/static` is copied into the Python runtime image (there is no Tailwind standalone CLI / `tailwind.config.js` anymore). `.dockerignore` excludes `frontend/node_modules`, `frontend/dist`, and the generated `app/static/{index.html,assets,favicon.svg,pcm-worklet-processor.js}`.
- The PCM AudioWorklet for live STT lives at `frontend/public/pcm-worklet-processor.js` and is served as `/static/pcm-worklet-processor.js` (referenced in `src/hooks/useStt.ts`).

## Key architecture facts

- App factory: `app/__init__.py:create_app()`. Qdrant client + collection creation run synchronously (needed immediately by document routes); loading the embedding model and building the vectorstore/retriever/agent happens in a background thread (`init_resources` → `_load_resources`) so container startup doesn't block on a model download. Code needing `app.extensions["agent"]`/`"dense_embeddings"` must gate on `wait_for_resources(timeout=...)` first (see `user_routes.py:trigger_ingestion`).
- Routes: `app/routes.py` (chat + SSE, no prefix), `app/api_routes.py` (JSON-API `/api/*` for the SPA), `app/user_routes.py` (`/user`, now legacy HTML routes + service-test helpers/constants). The former `/admin` blueprint was removed; dashboard, vector DB, settings, summaries, and uploads now live under `/user` (legacy) and `/api/*` (SPA).
- Database service singleton: `app/database_service.py:init_db_service()` / `get_db_service()`. Every method opens its own session and closes it in `finally` before returning — see the DetachedInstanceError gotcha below.
- Models: `app/models.py`. Settings model is the source of truth for runtime config.
- Settings resolution order: `settings_service.py` reads DB first, then `.env`/environment, then default. A stale DB row silently wins over a correct env var indefinitely — check the `settings` table first when an env var "doesn't take effect".
- Qdrant client factory: `app/utils/qdrant_client.py`. Connects to a running Qdrant server at `QDRANT_HOST:QDRANT_PORT` (default `localhost:6333`). No embedded/local file mode.
- Knowledge areas (`app/knowledge.py`, table `knowledge`): every area has its **own Qdrant collection** (`kb_<id>`). The seeded default area keeps the legacy collection `local_rag` and the legacy folders. `knowledge_paths()` resolves the per-area folders; structured data of non-default areas lives in `DATA_DIR/knowledge_<id>/` and is addressed by Pandas tools as `knowledge_<id>/<file>`. API endpoints take `?knowledge_id=` (omitted = default area). Collections are created via `app/vector/collections.py:ensure_collection`. Embedding config is copied from the global settings at creation (informational for now; all areas share the global embedding instance).
- Retrieval scope: the agent/retriever are singletons. `app/retrieval.py:MultiCollectionRetriever` reads the per-request `RetrievalScope` from a `ContextVar` that `/chat` sets inside the agent loop (`knowledge_ids` from the request body; `null` = all areas). Round-robin merge, no cross-collection scores. Without a scope it searches only `local_rag`.
- Access control (`app/access.py`, tables `groups`, `group_members`, `resource_grants`, flags `knowledge.is_public` / `model_configs.is_public`; user/group admin in `app/user_admin.py` + `app/user_admin_routes.py`): a knowledge area or model is accessible if the user is admin, the resource is public (read/use only), or a grant exists for the user or one of their groups (`write` implies `read`). Migration 0011 marks all pre-existing knowledge areas public (behavior unchanged); new knowledge starts private, the creator gets a `write` grant, new model clones start private (unconfigured base models are public). Rules to preserve: (1) every `knowledge_id` endpoint in `app/api_routes.py` goes through `_current_knowledge()` (read for GET, write otherwise) and is wrapped with `@knowledge_scoped`, which runs the check *before* the handler (inside a handler's `try/except Exception` the abort would turn into a 500); denials are 404 so IDs do not leak; (2) `/chat` intersects the requested `knowledge_ids` with `accessible_knowledge_ids(user)` and never trusts request collections, except knowledge attached to the chosen model, which anyone allowed to use that model may search (`can_use_model`); (3) non-admin `/api/models` is filtered by `can_use_model` and carries no config; (4) saving a knowledge share list never removes the saving non-admin's own write access; (5) deleting a user/group/knowledge/model/connection removes its grants. Last active admin, own role/status and self-delete are protected. Users change their own password via `POST /api/auth/change-password`. OIDC is not implemented.
- Retrieval profiles (`app/rag/`: `profiles.py` validated config + CRUD, `pipeline.py` stages, `queries.py` LLM question generation, `helper.py` helper LLM, `format.py` source-labelled tool output, `routes.py` API; tables `retrieval_profiles`, `knowledge.retrieval_profile_id`): a profile is chosen **only on the knowledge** (NULL = default profile, switching takes effect immediately, no re-ingestion; there is deliberately no profile on models). Pipeline: optional LLM query expansion -> `query_points` per question and collection (dense + BM25 prefetch, weighted RRF or DBSF) -> RRF merge -> optional rerank against the *original* question -> optional MMR -> top `final_k` -> optional neighbor chunks (`chunk_index`/`chunk_total`, only for data ingested since 0.1.0). Every optional stage falls back instead of failing (trace records it). Seeds: "Standard" (hybrid + `BAAI/bge-reranker-base` + neighbors=1, no extra LLM call), "Gründlich" (+ multi-query), "Schnell" (old behavior from `RETRIEVER_*`). Defaults were chosen by measurement on a German test corpus (13 questions, hit@1: hybrid 10, +bge-reranker-base 12, +jina-v2-multilingual 11, +multi-query no gain), so do not change them without re-measuring; the multilingual Jina model was *worse* than the English MiniLM on a small German check. Users should never have to pick a strategy: the choice is under "Erweitert" on the knowledge page. The global reranker preloads at startup (`model_settings.prepare`). Admin test endpoint `POST /api/retrieval/test` returns the stage trace.
- Qdrant collections (`app/vector/collections.py:ensure_collection`, the only place that creates them): dense vector with **HNSW** (`m=16, ef_construct=100`) and the BM25 sparse vector `langchain-sparse` with **`modifier=IDF`** (fastembed BM25 queries are all 1.0, IDF must come from the server; without it keyword search is much weaker). Existing collections without the modifier are upgraded at startup. Ingestion always writes both vectors; never drop either.
- LLM connections and models (`app/connections.py`, `app/llm/registry.py`, `app/llm/factory.py`, `app/admin_routes.py`; tables `connections`, `model_configs`): OpenAI-compatible endpoints (LiteLLM, vLLM, Ollama, OpenAI; Claude via LiteLLM) with base URL + API key (plaintext in SQLite like the other keys; never returned by the API; blank key on edit = keep, but only while the base URL is unchanged, and the stored key is only ever sent to the stored URL; link-local targets like 169.254.x.x are rejected, private LAN addresses are allowed). Models are fetched live from `<base_url>/models` (60 s cache). A model is addressed by ref `base:<connection_id>:<model_id>` or `clone:<config_id>`. `model_configs` holds per-model overrides (prompt appended to or replacing `DocumentAgent.SYSTEM_PROMPT`, sampling params over the global `CHAT_*` defaults, attached knowledge ids) and clones. `/chat` takes `model`; `registry.get_agent` builds and LRU-caches one `DocumentAgent` per model (cache key includes a signature of the whole config, so edits take effect without invalidation). A model with attached knowledge always searches exactly those areas and ignores the request's `knowledge_ids`. `DEFAULT_MODEL` (hidden from the settings UI) is the default; without it the legacy `CHAT_MODEL` on the first active connection is used. The seeded "Standard" connection comes from `CHAT_BASEURL`/`API_KEY` (`ensure_default_connection`, at runtime because fresh DBs have no settings rows during migrations). Vision/ingestion LLMs still use `VISION_*` and are not selected via connections.
- Chat attachments (`app/attachments.py`): uploaded via `POST /api/chat/attachments`, ingested in a background thread (fixed ingestion: no LLM context enrichment, no archive move) into collection `user_uploads` with `session_id` in the payload; search filters on it. Deleting a session removes them. Only document types (PDF/DOCX/DOC/ODT/MD), no CSV/Excel.
- Vector collection of the default area is `"local_rag"` and uses hybrid retrieval (`langchain_qdrant` dense + FastEmbedSparse BM25). One Qdrant point per chunk; all chunks of one ingested file share a `file_group_id` payload value, which file-level list/delete operations filter on (a file is never one point).
- Embedding dimension is never typed in: it is probed from the model (`models_runtime.get_embedder(spec).dimension`) and stored per knowledge (`knowledge.embedding_dimension`). `EMBEDDING_DIMENSION` is a dead legacy setting.
- Shared knowledge base, not per-user silos: any document uploaded by anyone is retrievable by everyone in chat (intentional). `UserDocument`/`UserSummaryFile` rows are ownership bookkeeping for the "my documents"/"my analyses" management UI, not an access-control boundary — retrieval is never filtered by uploader.
- `app/tools/custom_tools.py:CustomTools` is instantiated **once** at app startup and shared across every request — it has no per-request state. Summary tracking (`_track_summary_for_current_user`) calls `get_db_service()` directly (single-user, no Flask session inspection needed).
- Linux/Docker runs `gunicorn -w 1 --threads 4 -k gthread` (`run_linux.py`). Worker count must stay at 1 — several module-level globals are process-wide, not per-worker-safe (`app/__init__.py`'s `_qdrant_client`/`_db_service`, `app/user_routes.py`'s shared ingestion status). Threads exist so a long-lived SSE chat stream doesn't block every other request app-wide.
- Tailwind is **v4** compiled by the Vite plugin (`@tailwindcss/vite`) at `npm run build` time — there is no standalone CLI, no `tailwind.config.js`, and no live watch. Utilities are generated from `frontend/src/**` sources. The design tokens (ChatGPT-like neutrals) live in `frontend/src/index.css` under `@theme inline` (`--color-surface`/`--color-primary`/`--color-border-base` …) mapping raw `--rag-*` CSS vars; `.dark` overrides them (class-based dark mode). **Do not** add per-element `dark:` variants — extend the tokens instead. New utility classes only take effect after a rebuild (`cd frontend && npm run build`) or via `npm run dev` (Vite HMR).
- **Models are a registry** (`app/rag/models_runtime.py`): `ModelSpec{source: hf|endpoint|fastembed, model, connection_id}` -> cached embedder/reranker (`hf` = sentence-transformers `SentenceTransformer`/`CrossEncoder`, `endpoint` = OpenAI `/embeddings` and `POST /rerank` of a Connection incl. link-local block, `fastembed` = legacy only). Global specs live in settings `EMBEDDING_SPEC`/`RERANKER_SPEC` (`app/rag/model_settings.py`; fresh install = HF MiniLM + `bge-reranker-base`, upgraded installs = same models via fastembed, migration `0014`). Loading is lazy and in the background at startup/after saving (`status()` for the UI, failures cached 60 s). **Never embed without a spec**: each knowledge stores `embedding_spec` + `index_signature` (hash of model, chunk settings, `SPLITTER_VERSION`, `PARSER_VERSION`); queries (`RetrievalScope.specs`) and new ingestion use *the knowledge's* model, not the global one, so search stays correct until it is re-indexed. `model_settings.is_stale()` drives the "Index veraltet" banner. Chat attachments always use the current global model in `user_uploads_<hash>`. Admin UI: tab "Einlesen & Modelle" in the Administration modal (`AdminDialog`, all admin areas live there, no `/admin/*` routes), API `/api/admin/embedding*`. The profile's `rerank.model` is always `"default"` (global reranker).
- Document parsing uses **Docling** for PDF, DOCX/DOC/ODT; the wrappers return **Markdown** (`PreprocessBase.build_markdown_from_docling`: tables as Markdown or CSV reference blocks via `app/ingest/tables.py`, images as `[BILD-BESCHREIBUNG: ...]` through VisionLLM with phash dedup). `app/ingest/splitter.py` (`split_markdown`, `SPLITTER_VERSION`) splits by headers `#`-`####` (oversized sections recursively, small ones merged, table rows with repeated header; heading path prepended to the embedded text) and `app/ingest/indexer.py` (`build_points`, `PARSER_VERSION`) builds the Qdrant points. The Markdown is stored at `data/markdown/<knowledge_id>/<file_group_id>.md` (`UserDocument.markdown_path`), is viewable via `GET /api/documents/<id>/markdown` and is the source for re-indexing. Bump `SPLITTER_VERSION`/`PARSER_VERSION` when changing splitting/parsing so indexes become stale. `.md` uses LangChain `TextLoader`. `unstructured` and `python-docx` are fully removed.
- **Re-indexing** (`app/reindex.py`): background job, blue/green (`<collection>_g<n>` built next to the old one, swapped in one DB transaction via `knowledge.swap_collection`, old dropped, failure keeps the old one and sets `last_reindex_error`). Docs without stored Markdown are re-parsed from `processed_files`, else rebuilt from old chunks. While running, mutating calls on that knowledge return 409 (`_abort_if_reindexing`). The default knowledge's collection may be renamed (`local_rag_g1`): look it up by `is_default`, never by the literal `local_rag`. Endpoints `POST /api/knowledge/<id>/reindex`, `POST /api/reindex-all`, `GET /api/reindex/status`.
- **index.md per knowledge** (`app/ingest/index_doc.py`, `refresh_index`): auto-built table of contents the agent reads first (`read_knowledge_index` tool; small ones appended to the question). Kept because an A/B run (16 runs each) showed 16/16 vs 15/16 correct, 1.1 vs 2.2 tool calls, 22 vs 25 s. Switch `INGEST_INDEX_ENABLED`.
- The pandas tools only see the data folders of the knowledge selected in the chat (`RetrievalScope.data_dirs`, `CustomTools._allowed_files`); never widen that to the whole `DATA_DIR`.
- `langchain-huggingface` is **not** a dependency. Dense embeddings/rerankers come from the registry above; only the BM25 sparse model (`FastEmbedSparse("Qdrant/bm25")`) is fixed. `torch` **is** a direct dependency (CPU-only, pinned via `[tool.uv.sources]` to the PyTorch CPU wheel index) — needed by Docling and `sentence-transformers`, but listed explicitly so uv's source mapping applies (a purely transitive requirement ignores `[tool.uv.sources]`; see the inline comment in `pyproject.toml`). `pyproject.toml` pins the CPU wheel for local dev; the Docker image swaps in CUDA torch (`ARG TORCH_BACKEND`, default `cuda`) and compose reserves the GPU. Note `uv sync`/`uv run` reverts a CUDA-torch venv to the CPU wheel. Device choice lives in `app/utils/device.py` (`torch_device()`: cuda > mps > cpu, override `RAG_DEVICE`; `onnx_providers()` adds CoreML on macOS); `run_mac.py` is the macOS launcher: only the app runs natively (MPS needs the host), helper services stay in Docker via `docker-compose.mac.yml`. large models are slow on CPU.
- `gradio` and `sentence-transformers` are direct deps in `pyproject.toml` with **zero imports** in `app/`/`scripts/`/`parakeet/` (as of this writing). `sentence-transformers` is pulled transitively by other libs but unused directly; `gradio` appears unused entirely. Don't remove either blindly without checking `uv tree` — `sentence-transformers` may still be a transitive provider something resolves to.

## Document ingestion

Dokumente werden **über das Web-Interface** eingelesen. Es ist kein separates CLI-Skript mehr nötig.

- Dokumente-Bereich (`/user/documents`) und Vektordatenbank-Bereich (`/user/vectordb`): Dateien hochladen → **Ingestion starten**. Ingestion läuft synchron (`app.vector.DocumentIngestion.ingest_documents()`, aufgerufen aus `app/user_routes.py`) — der Request blockiert bis Ingestion fertig ist, kein Hintergrund-Job/Queue.
- **Strukturierte Daten (CSV/XLSX/XLS) werden NICHT als Inhalt in die Vektordatenbank ingestet.** Sie sind reine Pandas-Referenz: Der Upload (`store_uploaded_files` in `app/utils/file_manager.py`) legt sie sofort in `DATA_DIR` ab (Kollisionsschutz per Timestamp-Suffix) und listet sie über `/api/data-files`; genutzt werden sie ausschließlich über die Tools `list_files`/`preview_data`/`run_pandas`. **Pro Datei wird jedoch ein schlanker Verweis-Chunk** (`type='data_reference'`, `file_group_id=filename`) über `app.vector.ingestion.index_data_references()` in Qdrant geschrieben — mit Dateiname, Spalten, Zeilenzahl und dem Hinweis, dass Details per `run_pandas` zu holen sind (Text beginnt mit `[STRUKTURIERTE DATEN]`). So findet das Modell die Tabelle semantisch, ohne die Daten zu duplizieren. Der Verweis wird beim Upload (best-effort, nur wenn Embeddings geladen) und bei jedem „Ingestion starten" idempotent neu geschrieben; beim Löschen entfernt `delete_data_reference()` ihn. Nur Dokumente (PDF/DOCX/DOC/ODT/MD) landen in `data/files/` und werden als Volltext ingestet; nach Erfolg wandern sie nach `data/processed_files/`.
- Unter Windows wird Qdrant als `qdrant.exe` von `run_windows.py` gestartet (Server-Modus auf `127.0.0.1:6333`), sodass Flask und Ingestion gleichzeitig laufen können.

## Code conventions

- German UI, tool descriptions, system prompt, and user-facing errors.
- Imports grouped: stdlib → third party → local, separated by blank lines.
- Use `SettingsService` for config access; fall back to `os.getenv` only where the DB session is unavailable.
- Use `get_db_service()` for DB access; close sessions explicitly.
- Pydantic input models for LangChain tools, with German `description` fields.
- Path validation: resolve with `Path` and assert the result stays under `DATA_DIR`/`SUMMARIES_DIR`.
- Branch naming: `feat/...`, `fix/...`, `docs/...`. Run `uv run ruff check .` before opening a PR (see `CONTRIBUTING.md`).

## Security guardrails to preserve

- `run_pandas` tool blocks `os.`, `sys.`, `subprocess`, `__import__`, `open(`, `eval(`, `exec(`, and write methods like `to_csv`/`to_sql`/`to_json`.
- Do not relax these blocks without explicit user approval.

## Common gotchas

- **DB sessions:** `DatabaseService.get_session()` auto-closes sessions opened inside a request (`after_this_request`), but background threads must close their own. Never keep a long-lived session (`app.extensions["settings"]` is a `LiveSettingsService` that opens a short session per call) — a cached session returns stale settings and, on Postgres, holds a connection from the pool.
- **Postgres vs SQLite in migrations:** no `INSERT OR IGNORE`, no integer literals for booleans, no `lastrowid` (use `RETURNING`). Test migrations against a real Postgres (`TEST_DATABASE_URL=postgresql+psycopg://... pytest`; the suite recreates the schema per test).
- **Settings drift:** Admin panel edits live in the `settings` table and win over `.env`/environment variables silently and indefinitely — a stale DB row can override a correct env var forever. Check the `settings` table before trusting `.env` when something "doesn't take effect" (bit us with `QDRANT_HOST` stuck at `localhost` from an old run). `env.example` contains only Qdrant infra vars and OCR paths — all app config (LLM, embedding, retriever, storage, API keys, STT) lives in the `settings` table.
- **API_KEY no longer needs `.env`:** `API_KEY` is read from the settings DB (like all other config), with `os.getenv` only as standalone fallback. The `docker-compose.yml` no longer passes `API_KEY` as an environment variable. The settings DB row is seeded with default `'ollama'` on first migration.
- **Embedding dimension mismatch** makes Qdrant drop or reject points (the in-memory test client drops them silently): test fakes must expose `dimension` matching the collection. Model config lives in the `settings` table and the admin page, not in `env.example`.
- **Embedding backend change requires re-ingestion:** switching from Torch (`HuggingFaceEmbeddings`) to ONNX (`FastEmbedEmbeddings`) changes vector values for the "same" model — old and new vectors coexist in the collection with slightly different geometries. Re-ingest all documents after swapping backends.
- **Tesseract paths are NOT read from env anymore:** Docling OCR uses `TesseractCliOcrOptions` (CLI subprocess, configured in `preprocess_pdf.py` with `lang=["deu","eng"]` and the default `tesseract_cmd="tesseract"`). The `TESSERACT_CMD`/`TESSERACT_PATH`/`POPPLER_PATH` entries in `env.example` are now **dead** — no app code reads them. To point Docling at a custom Tesseract binary (e.g. Windows), pass `tesseract_cmd=...` to `TesseractCliOcrOptions` in code. Use `TesseractCliOcrOptions`, **never** `TesseractOcrOptions` (the latter needs the `tesserocr` Cython binding + `libtesseract-dev`/`libleptonica-dev` build headers — painful and unnecessary).
- **Qdrant must be running** before starting the app (server mode only; no embedded file fallback). On Windows, `run_windows.py` auto-starts `qdrant.exe`; on Linux, use Docker Compose or run Qdrant separately.
- **Qdrant server migration:** `scripts/manage_qdrant.py` (`uv run python scripts/manage_qdrant.py status|migrate|info`) can move a collection between two Qdrant server instances.
- **DetachedInstanceError risk:** `DatabaseService` methods close their session before returning ORM objects. Any relationship on a returned object (e.g. `ChatSession.messages`, `Message.session`) not eager-loaded (`joinedload`) raises `DetachedInstanceError` the moment it's accessed later — already happened once with `get_summary_by_filename` (a relationship access). Plain columns are always safe; relationships are not unless eager-loaded.
- **"Tracking" DB writes are easy to forget to wire up:** `add_document()`/`create_summary_file()` existed with zero callers for a while — files were written/ingested correctly but silently never appeared in the "my documents"/"my analyses" UI because nothing called the DB-row-creating method. When adding a "create X and track it" flow, grep for actual callers, don't assume it's wired in just because the method exists.
- **Gunicorn worker count:** stay at `-w 1` (see architecture facts above) — multiple worker processes would each get their own copy of the module-level globals several routes depend on.
- **fastembed mean-pooling change:** fastembed ≥0.6 switched `paraphrase-multilingual-MiniLM-L12-v2` from CLS-token to mean pooling. Vectors embedded with fastembed ≤0.5.1 (CLS) are NOT compatible with new embeddings — re-ingest all documents after upgrading fastembed. The `UserWarning` about this is intentionally suppressed in `app/__init__.py` (the new behaviour is correct); don't remove that filter without a reason.
- **torch CPU pin (uv):** `torch`/`torchvision` must stay direct deps in `pyproject.toml` (not just transitive) for `[tool.uv.sources]` to route them to the `pytorch-cpu` wheel index — a purely transitive requirement ignores source mapping and would pull the multi-GB CUDA wheel instead. The `explicit = true` on `[[tool.uv.index]]` scopes the index to only the mapped packages, so all other deps still resolve from PyPI. Don't "clean up" torch/torchvision out of `dependencies` without checking this.
- **SearXNG JSON API needs explicit opt-in:** `docker-compose.yml`'s `searxng` service is configured via the checked-in `searxng/settings.yml`. By default SearXNG only serves HTML and its bot-protection limiter blocks non-browser requests — both `search.formats: [html, json]` and `server.limiter: false` are required there, otherwise `web_search_tool.py`'s `format=json` requests come back empty/403. `server.secret_key` must NOT be left as `ultrasecretkey` — newer SearXNG images hard-refuse to start with that literal value instead of auto-generating a replacement (older versions did); the checked-in file has a pre-generated random hex value, regenerate your own with `openssl rand -hex 32` for real deployments. `SEARCH_SEARXNG_URL` defaults to `http://searxng:8080` on a fresh DB (migration `0004`).
- **entityguard PII-filter service:** `docker-compose.yml`'s `entityguard` service (`registry.nutsolution.de/entityguard:latest`, port `9500`, no host port mapped) is the PII-filter backend for `app/utils/pii_filter_client.py`. Its `/api/v1/sanitize` endpoint returns `mapping` as a **flat dict** `{"[NAME_1]": "Max Mustermann", ...}`, not a list of `{"placeholder":..., "original":...}` objects — `PIIFilterClient.demask()` handles both shapes (dict branch added after finding the mismatch would otherwise `AttributeError` on the first real call). `PII_FILTER_URL` defaults to `http://entityguard:9500/api/v1/sanitize` on a fresh DB (migration `0004`). `PII_FILTER_API_KEY` is sent as `Authorization: Bearer <key>` (not in the JSON body).
- **parakeet STT service needs a GPU (or explicit CPU build):** `docker-compose.yml`'s `parakeet` service (built from `parakeet/Dockerfile`, multi-stage `ARG DEVICE=gpu|cpu` selecting `nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04` vs `python:3.12-slim`) requires the NVIDIA Container Toolkit on the host for the GPU build — the `deploy.resources.reservations.devices` GPU reservation block works with plain `docker compose up` (no Swarm needed) as of Compose v2, but the container won't start without a real GPU + toolkit unless built with `--build-arg DEVICE=cpu`. The Dockerfile has a benign internal quirk: `ARG DEVICE=gpu` (before the first `FROM`, used to pick the base image) and a *separately re-declared* `ARG DEVICE=cpu` (inside the final stage, used only for an otherwise-unused `ENV DEVICE=${DEVICE}`) have different defaults — harmless as long as `docker-compose.yml` always passes `args: {DEVICE: gpu}` explicitly (which it does), since a single `--build-arg`/`args:` value overrides every `ARG` declaration of that name throughout the build. Models are preloaded at build time (Parakeet ASR into the default HF cache, Silero VAD into a flat `/app/models/silero-vad` dir — `onnxruntime` rejects the HF cache's symlink-into-`blobs/` layout for the raw VAD session driven directly in `streaming.py`). `STT_BASEURL`/`STT_MODEL` default to `http://parakeet:5001/v1`/`nemo-parakeet-tdt-0.6b-v3` on a fresh DB. **The actual seed source is `alembic/versions/0002_single_user_conversion.py`** (`ON CONFLICT(key) DO NOTHING` insert), not `app/database_service.py:_init_settings()` — that Python dict has its own STT entries too, but they're dead code for a fresh install: migration 0002 always runs first (`run_linux.py`/`run_windows.py` both run `alembic upgrade head` before starting the server) and already inserts the row, so `_init_settings()`'s "insert if not exists" check finds it present and skips it. Keep both in sync if changing STT defaults again — easy to edit only one and have it silently not take effect (this bit us once: editing `database_service.py` alone left fresh installs still pointing at the old `whisper` URL). The batch `/api/stt` route (`app/routes.py`) still works against this same URL and is kept as a server-side fallback, but the chat UI's mic button no longer calls it.
- **Live STT streaming needs `flask-sock` + a background relay thread:** `app/stt_stream.py` exposes `/ws/stt-stream`, a WebSocket endpoint (via `flask-sock`/`simple-websocket`, WSGI-socket-hijacking) that proxies raw float32 PCM from the browser to Parakeet's own `/v1/audio/stream` WebSocket (a plain synchronous `websocket-client` connection opened per browser session) and relays `partial`/`committed`/`final`/`error` JSON messages back. This only works under `gunicorn -k gthread` (the Linux/Docker path, `run_linux.py`) — **not** under `waitress` (`run_windows.py`), which has no socket-hijacking support, so live streaming STT is Docker-only; Windows users only get the batch `/api/stt` fallback. Each open recording occupies one of the app's 4 gunicorn threads for its whole duration (shares the pool with SSE chat streams) — fine for the single-user design, but don't lower `--threads` without checking this.
- **`parakeet/streaming.py`'s `ParakeetStreamEngine` must reuse `main.py`'s already-loaded ASR model, not load its own:** loading the ~0.6B-param Parakeet model a second time (one copy for the batch endpoint via `main.py`'s `get_model()`, a separate copy for the streaming engine) doubles GPU memory usage for the exact same weights — this OOM'd on a shared/modest GPU during verification (a 16MB Silero-VAD allocation failed only because the second ASR copy had already exhausted VRAM). Fixed by passing `asr_model=get_model()` into `parakeet_stream_engine.ensure_loaded()` in `main.py`'s lifespan handler; `ensure_loaded()`/`_load()` skip the redundant `onnx_asr.load_model()` call when given one. Also: the raw Silero VAD `onnxruntime.InferenceSession` in `streaming.py` is forced to `CPUExecutionProvider` regardless of the ASR provider — it's tiny (~2MB) and this avoids contending with the ASR model for GPU memory entirely.


## Models, vision and web search (current wiring)

- All chat/vision LLMs come from Connections (`app/llm/registry.py`); the legacy `CHAT_*`/`VISION_*`/`API_KEY` settings are hidden and unused for routing (sampling defaults in `app/llm/factory.py` still read `CHAT_*` as fallbacks). `VisionLLM` (`app/llm/local_llm.py`) resolves `VISION_MODEL_REF` (else the default model) on every call; it serves image descriptions and context enrichment. There is no startup "default agent" any more: `/chat` needs a resolvable model.
- Web search is a per-model tool (`ModelConfig.web_search`, migration 0015, default off). `app/tools/web_access.py` builds it from live settings and only if `SEARCH_SEARXNG_URL` and an enabled `PII_FILTER_URL` exist; the config API rejects enabling it otherwise (400), and `/chat` appends the tool per request (agent cache key includes tool names). The PII client is built per use, not at startup.
- Infrastructure settings (`DATA_DIR`, `SUMMARIES_DIR`, `QDRANT_*`) are env-only (`SettingsService.ENV_ONLY_KEYS`): the DB value is ignored, so docker-compose env wins over stale seeded values.
- Ingestion never fails silently: `DocumentIngestion.errors/warnings/processed` are returned by `POST /api/documents/ingest` and shown as toasts; a failed file stays in the input folder and its extracted table CSVs are deleted.

## My uploads (ownership and deletion)

- Ownership: `UserDocument.uploaded_by` (set by ingestion from a `<file>.uploader` sidecar written by `store_uploaded_files(..., uploader_id)`; the sidecar is consumed when the document is recorded) and `ChatAttachment.user_id` + `markdown_path`. Migration 0016; legacy knowledge documents have NULL and are not listed.
- `app/my_uploads.py` holds the shared logic: `delete_knowledge_document` (Qdrant vectors, original, Markdown, table CSVs, DB row, `refresh_index`) is used by both `DELETE /api/documents/<id>` (needs write access) and `DELETE /api/my-uploads/knowledge/<id>` (owner only, no knowledge role needed); `attachments.delete_attachment` handles chat attachments (vectors by `attachment_id` in every `user_uploads*` collection). Foreign items always answer 404.
- Chat attachments keep only the Markdown (`data/attachments/<session>/<id>/md/`); the original is deleted after ingestion. They still disappear with the chat (`cleanup_session_attachments`).
- UI: `MyUploadsPage` (`/uploads`, all roles). The dashboard and its `/api/stats` are gone.

- Tools admin page (`AdminToolsPage`, `/api/admin/tools`, `/api/admin/tools/test`) replaces the generic settings dialog: STT, PII filter and SearXNG only. The generic `/api/settings*` routes (except `change-password`) were removed; do not reintroduce raw-key settings UIs. Tests use the form values (`_FormSettings`) and only reuse the stored key for the stored URL.

## Chunk metadata (Qdrant payload)

- Per document chunk (`app/ingest/indexer.py:build_points` + `document_metadata`): `page_content` (embedded), `original_content`, `filename`, `source`, `title`, `headers` (list), `type`, `file_group_id`, `chunk_index`, `chunk_total`, `file_type`, `knowledge_id`, `uploaded_by`, `uploaded_at`, `parser_version`, `splitter_version`, plus `page_start`/`page_end` only when known. Attachments add `session_id`/`attachment_id`. Data-reference chunks (`type=data_reference`) carry `file_type`, `knowledge_id`, and for tables extracted from documents `source_document` + `table_number`.
- Page numbers (PDF only): `PreprocessBase.build_markdown_from_docling` exports with a page-break placeholder and replaces it with `<!--p:N-->` markers (`apply_page_marks`; dropped if the break count does not match the page count). `split_markdown` strips the markers first and finds each chunk's words in the document to set `page_start/page_end` (`_assign_pages`; repeated table headers inherit the previous page). Markdown without markers means no pages. No `SPLITTER_VERSION` bump: new fields are optional, old data simply lacks them.
- No payload indexes for the new fields (no filtering yet); add them in `ensure_collection` before building filters.

## Ingest task prompts (DB-driven)

- Prompts, models and parameters of the two LLM ingest tasks live in `settings` (category `ingest`): `VISION_PROMPT`, `VISION_MODEL_REF`, `VISION_TEMPERATURE`, `VISION_MAX_TOKENS`, `INGEST_VISION_ENABLED`, and `CONTEXT_PROMPT` (placeholders `{dokument}`, `{abschnitt}`), `CONTEXT_EXCERPT_CHARS`, `CONTEXT_MODEL_REF`, `CONTEXT_TEMPERATURE`, `CONTEXT_MAX_TOKENS`, `INGEST_CONTEXT_ENRICHMENT`. `Setting.default_value` holds the standard prompt ("reset" reads it from there). Migration 0018 seeds them; `app/ingest/prompts.py` holds the seed texts only (fresh SQLite/test DBs and last-resort fallback) — never use them as runtime source.
- `app/ingest/tasks.py` (`load_task`, `render_context_prompt`, `validate_prompt`) reads the DB on every call; `TaskLLM(task)` (`app/llm/local_llm.py`, alias `VisionLLM`) resolves model and parameters per call. `DocumentIngestion.model` = vision, `.context_model` = context. Admin API: `tasks` in `/api/admin/embedding`.
- New LLM prompts or tunables belong in `settings` plus an Alembic migration, not in code.

## External sources (foreign vector stores, read-only)

- A foreign Qdrant is a Knowledge with `kind='external'` (migration 0019) and `source_config` JSON (`url`, `api_key`, `collection`, `dense_vector`, `sparse_vector`, `fields` mapping). Its collection_name is `ext_<id>` and is never created or deleted locally; the real collection is `source_config.collection`. `embedding_spec`/`embedding_dimension` hold the model **the admin declared** — nothing is auto-detected.
- `app/vector/sources.py`: `parse_config`, `connect` (read client, `_reject_link_local`, timeout), `probe_source` (facts only), `validate_source` (hard checks: vector exists, dimension, text field, and a sample-point cosine check against the declared model, `MIN_SIMILARITY=0.8`), `normalize_payload`, `layout_for`. Retrieval: `RetrievalScope.externals` -> `MultiCollectionRetriever._run_external` -> `pipeline.run(layout=...)` (dense/sparse vector names, payload normalization, neighbors only with default `chunk_index`/`group` fields; without a sparse vector the search is dense-only). A down source never fails the chat: `scope.warnings` -> SSE `warning` event.
- Read-only everywhere: `_current_knowledge()` answers 409 for write requests and `/api/vectordb*` on external knowledge; reindex/stale/`ensure_collection`/index.md skip them; deleting only removes the row. Only admins create/change them; `source_config` is scrubbed to `{..., has_key}` in all API responses. Tests use a fake foreign server that refuses writes (`tests/test_external_sources.py`).
- Other store types (pgvector, OpenSearch, Chroma …) later: new `kind` values behind the same layout idea.

- Per-user/group filtering of external sources: `source_config.access` (`enabled`, `user_field`/`user_attr`, `group_field`/`groups_from`, `static`, `admins_unfiltered`). `sources.build_filter(cfg, identity)` returns `(qdrant Filter | None, blocked)`; `blocked` means the source returns nothing (fail closed). The filter is passed as `query_filter` to `pipeline.run` and re-applied to neighbor scrolls (`_expand_neighbors(..., extra_filter)`). Identity = `RetrievalScope.identity` (`username`, `display_name`, `groups` from `access.user_group_names`, `external_groups`, `is_admin`), filled in `app/routes.py`. Name matching is exact in Qdrant, so `_variants` sends common casings.

## Login with LDAP / OIDC (external accounts)

- Config lives in the DB (migration 0020): settings `AUTH_LDAP`, `AUTH_OIDC` (JSON, sensitive), `AUTH_DEFAULT_ROLE`, `AUTH_AUTO_CREATE`, `APP_BASE_URL`; user columns `auth_source` (`local|ldap|oidc`), `external_id`, `external_groups` (JSON, all group names the provider reported); `group_members.external` marks memberships set by a login. `app/auth_external.py` (config load/save with "empty secret = keep", `group_name_from`, `sync_groups`, `login_external_user`), `app/auth_ldap.py` (ldap3; `CLIENT_STRATEGY` is the test seam for `MOCK_SYNC`), `app/auth_oidc.py` (discovery cache, PKCE/state/nonce in the session, JWKS verification with PyJWT). API: `/api/auth/providers`, `/api/auth/oidc/login|callback`, `/api/admin/auth` (+`/test`).
- **Rule: groups are never imported.** `sync_groups` only matches provider group names (case-insensitive, DN -> CN) against **existing** local groups and never creates one; it only removes memberships with `external=True`. Roles never come from groups; new external accounts get `AUTH_DEFAULT_ROLE`.
- Local login always works and wins: a local account is only checked locally, an external login whose name collides with a local account is refused, external accounts have no password login/change (`users.authenticate`, `verify_password`, `set_password`). LDAP errors never block local login. Tests: `tests/test_external_auth.py` (ldap3 mock + a local fake OIDC provider with RSA-signed tokens).
